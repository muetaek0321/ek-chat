# Technical Debt Audit

## 1. 目的

FastAPI 製の `backend` と Next.js 製の `frontend` で構成された本プロジェクト内の技術的負債を発見し、保守性、変更容易性、信頼性、安全性、開発効率、パフォーマンスに与える影響を評価する。

単なるスタイルの指摘にとどまらず、将来的な変更コストや不具合リスク、API連携の不整合、設計方針からの逸脱を優先的に検出する。

本スキルは**調査とレポート作成のみ**を行う。ソースコードの修正、リファクタリング、パッケージ更新、設定変更などの変更操作は一切行わない。

調査結果はMarkdownファイルとして、プロジェクトルート直下の `technical_debt_report.md` に出力する。あわせて会話内でも調査完了の報告とともにサマリーや推奨アクションを提示する。

## 2. 基本原則

- 実際のコード、設定、テスト、依存関係を根拠に判断する。
- リポジトリ直下および `backend/AGENTS.md`、`frontend/AGENTS.md` の設計方針・コーディング規約を基準として評価する。
- 問題の場所、根拠、影響、改善案を具体的に示す。
- 推測と確認済みの事実を明確に区別する。
- 単なる好みのコーディングスタイルを理由に負債と判定しない。
- 既存の動作仕様やフレームワークの意図を把握せずに設計を誤りと断定しない。
- 同一原因による重複指摘は統合する。
- 重要度、確信度、修正コストを分けて客観的に評価する。
- 判断材料が不足する場合は、要確認事項として報告する。
- 静的解析ツールの警告の有無だけで技術的負債の有無を断定しない。
- 指定範囲を優先し、関連箇所の確認が必要な場合のみ調査範囲を限定的に拡張する。
- 過去の調査結果との比較を前提とせず、毎回独立した監査として実施する。

## 3. 読み取り専用の制約

### 3.1 許可する操作

- ソースコード、テスト、設定ファイル、ドキュメントの読み取り
- ファイル構成、参照関係、依存関係の確認
- Gitの履歴や差分の参照
- 対象ディレクトリでの読み取り専用の静的解析ツールの実行（`uv run ruff check`、`yarn lint`、`yarn tsc --noEmit` など）
- 既存環境を利用した安全な依存関係検証（`uv lock --check`、`uv pip check` など）
- レポートファイル `technical_debt_report.md` の作成・更新
- 調査結果サマリーの会話内での提示

### 3.2 禁止する操作

- ソースコード、テスト、設定ファイルの編集・削除
- 自動修正・フォーマット（`uv run ruff check --fix`, `uv run ruff format`, `yarn lint --fix`, `yarn prettier --write` 等）
- パッケージのインストール、追加、更新、削除（`uv add`, `uv remove`, `pip install`, `yarn add`, `yarn remove`, `yarn install` 等）
- ロックファイルや仮想環境、ビルド成果物の更新・再生成（`uv sync`, `uv lock`, `yarn build` 等）
- データベースや外部サービスへの書き込み
- Gitのコミット、ブランチ変更、リセット、チェックアウト
- 調査対象プロジェクトの設定変更
- レポートファイル（`technical_debt_report.md`）以外の新規ファイル作成・編集・削除
- 調査のためだけに実行する、動作や副作用が未確認のスクリプト実行

コマンドを実行する場合は、必ず実行対象、カレントディレクトリ、副作用の有無を確認する。副作用が懸念される場合はコマンド実行を見送り、静的なコード調査で代替する。

## 4. 調査対象

本プロジェクトのアーキテクチャ（FastAPI + Next.js）に基づき、以下の観点から負債を調査する。

### 4.1 アーキテクチャと責務分離

- **共通・連携面**:
  - バックエンドとフロントエンドの境界設計、APIインターフェース設計の不整合
  - 責務の重複（バリデーションやフォーマット処理の無秩序な多重実装など）
- **Backend (FastAPI)**:
  - エンドポイント（`routers/`）、業務ロジック・サービス（`modules/`）、データモデル（`schemas/`）の分離
  - 単一クラス・モジュールへの責務集中（`ChatManager` などの巨大化・密結合）
  - LLMモデル拡張規約の遵守状況（`ResponseGenerator` を継承し、`setup()`, `cleanup()`, `get_parameters()`, `update_parameters()`, `__call__()` を適切に実装しているか）
  - 循環インポートや不明瞭な依存関係
- **Frontend (Next.js / React)**:
  - Server Component と Client Component の境界設計（不要な `'use client'` の付与によるバンドル肥大化）
  - Server Action（`'use server'`）の適切な利用と配置
  - コンポーネントの単一責任原則、表示ロジックと状態管理の分離
  - API通信ユーティリティの利用徹底（直接 `fetch` を呼ばず `@lib/fetchData` を利用しているか）
  - パスエイリアス（`@types`, `@styles`, `@components/*`, `@lib/*`）の活用状況

### 4.2 可読性と保守性

- 過度に深いネストや複雑な条件分岐
- 不明瞭な命名や暗黙的な前提
- 巨大なコンポーネント（数百行を超える単一TSXファイル）や長大な関数
- マジックナンバーやハードコードされた定数
  - Backend: 定数や Enum（`StrEnum` 等）の未定義
  - Frontend: `app/styles.ts` や `app/theme.ts` のテーマカラー・トークンを無視した直接のカラーコード・スタイル指定
- ドキュメンテーションの不足・陳腐化
  - Backend: 公開 API や主要関数に対する Google スタイル Docstring の欠如
  - Frontend: 複雑なロジックに対する JSDoc や意図を補うコメントの欠如

### 4.3 重複と冗長性

- Backend の Pydantic スキーマ（`EndpointModel`）と Frontend の型定義（`app/types.ts`）の不整合や二重管理によるドリフト
- 重複するデータ変換処理や入力バリデーション
- Frontend 内でのスタイル・UIパターンの重複定義（共通コンポーネントや共通スタイルの未活用）
- 未使用コード、到達不能コード、デッドコード
- 同一機能を実現する重複した実装やライブラリ

### 4.4 エラー処理とリソース・ログ管理

- **Backend**:
  - `print` 文の混入（`modules.logger.get_logger` または `modules.logger.get_endpoint_logger` を使用しているか）
  - 例外の握りつぶしや広すぎる `except Exception`
  - FastAPI の `HTTPException` やカスタム例外ハンドラによる適切なエラーレスポンスの欠如
  - LLMストリーミングやファイルハンドル、GPU/モデルリソースの解放漏れ
- **Frontend**:
  - APIレスポンス（`ApiResponse<T>`）のエラーハンドリング不足
  - 非同期処理におけるローディング状態（`isRunning` 等）、エラー表示、空状態（Empty State）の考慮漏れ
  - エラーバウンダリの不足による画面全体のクラッシュリスク

### 4.5 型とデータ設計

- **Backend (Python / Pydantic)**:
  - 関数の引数・戻り値における型ヒントの欠如
  - `modules.schema.EndpointModel`（camelCase <-> snake_case 変換）の継承漏れ
  - 内部処理における `dataclass` と API 用 Pydantic モデルの使い分けの乱れ
  - `Any` の過剰利用
- **Frontend (TypeScript)**:
  - `tsconfig.json` の strict 設定に反するコード
  - `any` 型や不要な型アサーション（`as`）の散見
  - バックエンド連携のデータ型や設定型が `app/types.ts` (`@types`) に集約されていない
  - 型定義と実際のAPIレスポンス構造の乖離

### 4.6 テスト品質

- **Backend (Pytest)**:
  - 主要な業務ロジックやエンドポイントに対するテストの不足
  - 外部API通信、LLMモデル推論、GPU依存処理が `unittest.mock` (`patch`) で適切にモック化されていないことによるテストの不安定さ・低速化
  - 境界値・異常系の検証不足
- **Frontend (Vitest / React Testing Library)**:
  - コンポーネントやカスタムフックの単体・統合テスト不足
  - `@lib/fetchData` の通信モック化（`vi.mock`）の不備
  - アクセシビリティ観点（RoleやLabel）に基づかない実装詳細依存のテスト
- **共通**:
  - テスト間の実行順序依存や環境依存

### 4.7 依存関係とパッケージ管理

- **Backend (uv)**:
  - `uv.lock` と `pyproject.toml`（`dependencies`, `dependency-groups`）の不整合
  - `.python-version` (>=3.13) と `pyproject.toml` の `requires-python` の不一致
  - 不要または未使用の依存パッケージ
- **Frontend (yarn)**:
  - `yarn.lock` と `package.json`（`dependencies`, `devDependencies`）の不整合
  - 開発用依存と本番用依存の混在
  - 非推奨パッケージや重複した機能を持つライブラリの共存

### 4.8 設定と構成

- `.env` と `.env.example` の乖離
- APIキー、トークン、接続情報などの機密情報のハードコード
- 環境依存値（APIエンドポイントURL、ポート番号等）の直接埋め込み
- Next.js 設定（`next.config.ts`, `tsconfig.json`, `postcss.config.mjs` 等）の過不足・不整合

### 4.9 セキュリティと信頼性

- 外部入力（リクエストボディ、URLパラメータ、プロンプト）の検証不足
- CORS設定の過度な緩和や認証・認可の検証漏れ
- プロンプトインジェクションに対する考慮やサニタイズ
- XSS や危険な HTML レンダリング（`dangerouslySetInnerHTML` や Markdown レンダリングのサニタイズ）
- 機密情報のログ出力（プロンプトや個人情報、APIキー）

### 4.10 パフォーマンス

- **Backend**:
  - 不必要なメモリコピー、大量データの一括読み込み（イテレータ・ジェネレータ・チャンクストリーミングの未活用）
  - 同期ブロッキング処理によるイベントループの遅延
- **Frontend**:
  - 不要な再レンダリングや非効率な React State 構造
  - クライアント側バンドルサイズの肥大化（重いライブラリのClient Componentでのインポート）
  - デスクトップ・モバイルでのレスポンシブデザインの崩れやレイアウトシフト

## 5. 調査範囲の決定

### 5.1 調査スコープの指定

- **プロジェクト全体**: `backend/` と `frontend/` の両方を調査し、スタック横断の課題（API連携、型整合性など）も含めて監査する。
- **Backend 指定**: `backend/` ディレクトリ配下（FastAPI、Pytest、uv環境）を集中的に調査する。
- **Frontend 指定**: `frontend/` ディレクトリ配下（Next.js、Vitest、yarn環境）を集中的に調査する。
- **特定モジュール・ディレクトリ指定**: 指定されたディレクトリ（例: `backend/routers/`, `frontend/app/database/` など）を優先して調査する。

調査範囲外の情報が必要な場合（例: APIエンドポイント変更の影響をフロント側で確認する場合）は、必要最小限の関連箇所のみを確認し、その理由をレポートに記載する。

### 5.2 除外対象

原則として以下は調査対象から除外する。

- **Backend**: `.venv/`, `.ruff_cache/`, `.pytest_cache/`, `__pycache__/`
- **Frontend**: `node_modules/`, `.next/`, `tsconfig.tsbuildinfo`
- **共通**: `.git/`, 一時ファイル、ビルド成果物

## 6. 静的解析ツールの活用

### 6.1 基本方針

各領域のコマンドは、**必ず対象ディレクトリ（`backend/` または `frontend/`）に移動して実行する**。

- `backend`: パッケージ管理 `uv` を使用するため、コマンド実行は必ず `uv run` を経由する。
- `frontend`: パッケージ管理 `yarn` を使用するため、コマンド実行は `yarn` を経由する。

自動修正（`--fix`）やフォーマット（`format`）などの変更操作は絶対に指定しない。

### 6.2 推奨コマンド例（読み取り専用）

#### Backend（`backend` ディレクトリで実行）

```bash
# Ruff 静的リント検証（変更を防止するため --no-fix を明示）
uv run ruff check --no-fix .

# ロックファイルと依存関係の整合性確認
uv lock --check
uv pip check

# テスト定義の収集（構文・インポートエラーの検出。テストは実行されないため副作用なし）
uv run pytest --collect-only

# 安全な単体テスト実行（副作用がないことが明らかな場合のみ）
uv run pytest
```

#### Frontend（`frontend` ディレクトリで実行）

```bash
# ESLint による静的解析（修正オプションなし）
yarn lint

# TypeScript 型チェック（ファイル出力を行わない --noEmit）
yarn tsc --noEmit

# Vitest 単体テスト実行（副作用がないことが明らかな場合のみ）
yarn test run
```

### 6.3 結果の解釈

ツールの警告やエラーをそのまま技術的負債として鵜呑みにせず、実際のコードと設計原則（`AGENTS.md`）に照合して実際の影響と重要度を判断する。

ツールを実行できなかった場合は、未実行の理由（環境未構築、依存関係未インストール等）をレポートに明記する。

## 7. 指摘の検証と評価

### 7.1 重要度 (Severity)

- **Critical**: 重大なセキュリティ脆弱性、データ損失、サービス全体の停止につながる重大な問題。
- **High**: 主要機能の信頼性や保守性に大きな影響を与え、将来の変更コストや障害発生率を著しく高める問題（例: APIスキーマの重大な不整合、リソースリーク、モック化されていない重いテスト）。
- **Medium**: 将来の変更容易性や可読性を低下させる問題（例: コンポーネント肥大化、共通スタイルの未活用、エラー処理の甘さ、型注釈の不足）。
- **Low**: 影響が限定的で、小規模な改善によって解消できる問題（例: 軽微な命名の揺れ、未使用の内部ヘルパー）。

### 7.2 確信度 (Confidence)

- **High**: コードや設定から直接確認でき、再現性・根拠が明確。
- **Medium**: 兆候は確認できるが、実行時の挙動や環境依存の検証が必要。
- **Low**: 推測の要素が大きく、仕様や要件の確認が必要。

### 7.3 修正コスト (Effort)

- **Small**: 局所的な修正（単一ファイル内、数行〜数十行の変更）で完了する見込み。
- **Medium**: 複数ファイルの変更や、関連テスト・型の修正が必要な見込み。
- **Large**: アーキテクチャやディレクトリ構成の見直し、複数モジュール・コンポーネントに跨る改修が必要な見込み。

## 8. レポートの出力形式

調査結果はMarkdown形式でプロジェクトルート直下の `technical_debt_report.md` に出力する。
完了後、会話内でもサマリーおよび最優先で対応すべき推奨アクションを提示する。

`technical_debt_report.md` の構成は以下の通りとする。

```markdown
# 技術的負債 監査レポート

## 1. エグゼクティブサマリー
- 調査対象およびスコープ（全体 / Backend / Frontend / 特定モジュール）
- 発見された負債の統計（全体件数、重要度別内訳、Backend/Frontend別内訳）
- 主要なリスクと全体的なコード品質の総括
- 最優先で対処すべき重要課題の要約

## 2. 負債一覧

### [TD-001] タイトル
- **対象コンポーネント**: Backend | Frontend | 共通
- **分類**: アーキテクチャと責務分離 | 可読性と保守性 | 重複と冗長性 | エラー処理とリソース管理 | 型とデータ設計 | テスト品質 | 依存関係とパッケージ管理 | 設定と構成 | セキュリティ | パフォーマンス
- **重要度**: Critical | High | Medium | Low
- **確信度**: High | Medium | Low
- **修正コスト**: Small | Medium | Large
- **対象箇所**: `path/to/file.ext` (L12-L34)
- **現状と根拠**: 具体的なコードや設定の状況、規約との乖離
- **影響**: 保守性、信頼性、パフォーマンス等への具体的な悪影響
- **改善案**: 具体的な改善方針や推奨コード設計
- **補足**: 前提条件や要確認事項

（以下、重要度順に記載）

## 3. 推奨アクションロードマップ
1. **即時対応（フェーズ1）**: セキュリティ・信頼性リスク、重大なAPI連携不整合
2. **中期対応（フェーズ2）**: アーキテクチャの整理、責務分離、型定義の共通化・厳格化
3. **継続的改善（フェーズ3）**: テスト拡充、スタイル重複の解消、リファクタリング

## 4. 要確認事項
- コードからのみでは仕様や意図が判断できなかった事項
- 実行環境や外部連携の制約により検証できなかった事項

## 5. 調査スコープと制約
- 確認したディレクトリおよび主要ファイル
- 実行した静的解析ツールとその結果
- 実行を見送った検証とその理由
- 除外した領域
```

## 9. 出力上の注意

- 重要度の高い指摘から順に出力する。
- 1つの根本原因による問題を細切れに多数の指摘へ分割せず、根本原因ごとにまとめる。
- 改善案は本プロジェクトの技術スタック（FastAPI, Pydantic, Next.js, React 19, MUI, Tailwind, uv, yarn）および `AGENTS.md` の方針に適合させる。
- 推測や確認できていない結果を捏造しない。
- レポート作成後、会話内で主要なポイントを簡潔に報告する。

## 10. 呼び出し例

ユーザーが以下のように要求した際に本スキルを起動する：

- `技術的負債を調査して`
- `このプロジェクトのコード品質や負債を監査して`
- `backendのFastAPI周りの設計や負債をレビューして`
- `frontendのNext.jsコンポーネントや型定義の課題をレポートして`
- `API連携や型定義に問題がないか監査して`
- `リファクタリングすべき箇所の優先順位を分析して`
